# DailyHealth

A PowerShell module that collects health and status information from infrastructure
systems and normalizes the results onto one status vocabulary (`success`, `warning`,
`error`, `info`), so unrelated sources can be summarized and reported on together.

> **A note on how this was built:** the code in `DailyHealth.psm1` is human-written.
> The comment-based help attached to every function — the `.SYNOPSIS`, `.DESCRIPTION`,
> `.PARAMETER`, `.OUTPUTS`, `.EXAMPLE`, and `.NOTES` blocks — was generated by an AI
> assistant reading that code, and this README was too. The assistant did not write or
> modify any of the module's logic. Treat the help and this document as a best-effort
> description of the code's behavior, not as a specification it was written to meet —
> and if you find a place where they disagree, assume the code is correct and open an
> issue on GITHub .


## What it does

`Get-DailyStatus` is the orchestrator. Give it a job configuration collection (normally
read from a JSON file) and it dispatches each entry to the matching collector function as
a background job, waits for them to complete, and returns one summarized record per job:
a severity count, a single worst-case health value, and the collector's raw results.

Every collector reports failures as data — a row with `Status = 'error'` — rather than
throwing, so one unreachable system doesn't take down the rest of the run.

## Collectors

| Type     | Function                     | Checks |
|----------|-------------------------------|--------|
| `SSL`    | `Get-CertExpiration`          | Public TLS endpoint certificates, and/or internally issued certificates from an AD CS hierarchy |
| `URL`    | `Test-URIList`                | HTTP/HTTPS reachability, optionally through one or more proxies |
| `DNS`    | `Test-DNSServerRemote`        | Name resolution against a set of DNS servers |
| `VEEAM`  | `Get-AllVBRJobs`               | Veeam Backup & Replication job results (VM jobs, agent jobs, agent copy jobs) |
| `VMWare` | `Get-TriggeredVMWareAlarms`   | vCenter triggered alarms |
| `UCS`    | `Get-UCSHealth`                | Cisco UCS Manager faults |
| `AGO`    | `Get-AGOStatus`                | ArcGIS Online service status feed |
| `SWN`    | `Get-SWISNodesDown`            | SolarWinds Orion nodes in a down state |
| `SWI`    | `Get-SWISInterfacesDown`      | SolarWinds Orion interfaces in a down state |
| `SWA`    | `Get-SWISAlerts`               | SolarWinds Orion active alerts |
| `HVAC`   | `Get-HVACAlerts`               | Building HVAC controller active alarms |

Each collector can also be called directly, outside of `Get-DailyStatus`, if you only need
one check. See that function's own help (`Get-Help <FunctionName> -Full`) for its
parameters and output shape.

## Requirements

- Windows PowerShell 5.1 (the module relies on `ICertificatePolicy`, which is not
  available in PowerShell 7+)
- [PKITools](https://www.powershellgallery.com/packages/PKITools) 1.6 or later, for the
  internal certificate check
- Whichever vendor modules correspond to the checks you actually run:
  - VMware PowerCLI, for `VMWare`
  - `Cisco.UCS.Common` and `Cisco.UCSManager`, for `UCS`
  - `SwisPowerShell`, for `SWN`, `SWI`, and `SWA`
  - Veeam PowerShell (on the VBR server itself), for `VEEAM`

  These are not declared as hard module dependencies, so the module will import without
  them; you only need the module for a vendor whose check you're actually configuring.
- Network reachability and credentials/sessions appropriate to whatever you're checking
  (PowerShell remoting to target hosts for `URL` and `DNS`; a saved UCS session and key
  file for `UCS`; and so on)

## Installation

Copy the whole `DailyHealth` folder — including its `1.1.0` subfolder — to any location
on `$env:PSModulePath`. The version-numbered subfolder is part of the repo layout already;
don't flatten it or copy only the files inside it, or the module will not load:

```
C:\Program Files\WindowsPowerShell\Modules\DailyHealth\1.1.0\DailyHealth.psd1
C:\Program Files\WindowsPowerShell\Modules\DailyHealth\1.1.0\DailyHealth.psm1
```

A later version would arrive as its own version-numbered subfolder alongside `1.1.0`, not
in place of it.

Then:

```powershell
Import-Module DailyHealth
Get-Command -Module DailyHealth
```

## Configuration

`Get-DailyStatus` takes its job list as a `-StatusConfig` object — normally the result of
reading and parsing a JSON file:

```powershell
$Config = Get-Content .\DailyHealth.json -Raw | ConvertFrom-Json
Get-DailyStatus -StatusConfig $Config
```

An example configuration file, `DailyHealth.json`, is included alongside the module with
one entry for every supported job type. Copy it, delete the job types you don't need, and
fill in your own hostnames, servers, and file paths — the placeholder values in it
(`example.com`, `FILE01`, `VEEAM01`, and so on) will not resolve or connect to anything.

Each entry in the file has four properties:

```json
{
    "JobNumber": 10,
    "Type": "SSL",
    "Description": "Public certificate expiration",
    "JobParameters": {
        "DomainList": ["portal.example.com", "www.example.com"]
    }
}
```

- **`JobNumber`** — sort order for the returned results. The example file steps by ten so
  entries can be inserted later without renumbering everything after them.
- **`Type`** — one of the type codes in the table above, matched case-insensitively.
- **`Description`** — a short label for the job, returned alongside its results.
- **`JobParameters`** — an object whose properties are splatted directly at the
  collector function. These must match that function's own parameters exactly; there's no
  validation before the call, so a misspelled or unsupported parameter name fails the job
  rather than being ignored. Check the collector's own help for its full parameter list.

Two things about `JobParameters` are easy to get wrong from JSON:

- **No `null` values.** A `null` anywhere inside `JobParameters` causes the parameter
  conversion to throw before the job is even dispatched. Omit a parameter entirely rather
  than setting it to `null`.
- **`DNSServer` is an array of objects, not an array of strings** — `{"IP": "10.10.1.10"}`,
  not `"10.10.1.10"`. `Test-DNSServerRemote` (via `Get-DailyStatus`) expects that shape and
  casts the `.IP` property to `[ipaddress]` itself.

Optionally, pass `-Credential` and/or `-JobTimeOut` to `Get-DailyStatus` to apply one
credential to every job's parameters, or to change how long (in seconds) a single check
may run before it's abandoned and reported as an error:

```powershell
Get-DailyStatus -StatusConfig $Config -Credential $SvcCred -JobTimeOut 600
```

## Output

`Get-DailyStatus` returns one object per configured job, sorted by `JobNumber`:

| Property        | Meaning |
|-----------------|---------|
| `Description`   | The job's label, as configured |
| `JobNumber`     | As configured |
| `Index`         | Zero-based position after sorting by `JobNumber` |
| `Results`       | The collector's raw output |
| `Summary`       | `Info` / `Success` / `Warning` / `Error` counts across `Results` |
| `OverallHealth` | A single worst-case value: `error` if any row is an error, else `warning` if any row is a warning, else `success` if any row succeeded, else `info` |

```powershell
Get-DailyStatus -StatusConfig $Config |
    Where-Object OverallHealth -in 'warning', 'error' |
    Select-Object Description, OverallHealth, Summary
```

## Known limitations

- Requires Windows PowerShell 5.1; will not run under PowerShell 7+.
- Certificate validation for the `SSL` check's external path is deliberately bypassed
  (inside `Invoke-WebRequestDH`) so that expired and untrusted certificates can be read
  and reported rather than failing the connection outright. This changes
  `[System.Net.ServicePointManager]` process-wide for the duration of each request; see
  that function's `.NOTES` for the specifics.
- `Get-AllVBRJobs` and `Get-DailyStatus` deliberately disagree on how an empty result set
  is treated (`warning` vs. `error`); see `Get-AllVBRJobs`'s `.NOTES`.
